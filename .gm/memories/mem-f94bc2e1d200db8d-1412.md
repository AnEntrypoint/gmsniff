plugkit verb asymmetry that silently corrupts a store: prd-add UPSERTS on an existing id (response {rescoped: id}, position and dependents preserved), but mutable-add with an existing id APPENDS a second row instead (response {added: id}). Re-scoping a mutable therefore produces two rows sharing one id, and if the point of the re-scope was to correct a wrong earlier finding, the refuted claim and its correction end up sitting in the file as separate standalone rows -- a reader can hit the stale one first, which is the exact contradictory-store failure the correction was meant to prevent, silently created by the correction itself. Measured on gmsniff: mutables.yml went from 11 rows to 12 with mut-browser-witness-client-edits at both line 17 and line 51, and nothing errored. Fix by dropping the stale block with a guarded script that ABORTS unless the row it keeps contains the corrective text, then re-parse to confirm unique ids. Also measured while fixing it: gmsniff's .gm/mutables.yml is LF-terminated, not CRLF, so a CRLF assumption is not universal even on Windows. gmsniff's own writer is NOT affected -- src/registry.js rewriteRow(text, id, fields) takes and returns file TEXT (not a path, and it does not write; passing a path makes it silently return null and change nothing), upserts in place leaving sibling rows byte-identical, and returns null for an unknown id rather than appending one.
